# Белый экран на Netlify: диагностика

20 октября 2026, ветка `multiplayer`. Deploy, push и commit не выполнялись. Игровые правила, Worker, протокол и WebSocket не изменены.

## Установленные факты

Сайт [hangul-durak.netlify.app](https://hangul-durak.netlify.app/) проверен настоящим Chrome из доступной среды. Главная страница вернула 200, React отрисовал главное меню, ошибок JavaScript при этой проверке не было. Это **не проверка из России**, и она не исключает проблему доставки файлов на российском устройстве.

До диагностических изменений опубликованный JS и локальный production JS совпали побайтово после замены единственного отличия — публичного адреса сервера комнат. На Netlify указан production Worker, локальная проверочная сборка использует локальный endpoint. Таким образом, признаков устаревшего кода приложения на сайте не обнаружено. Привязку проекта к ветке в настройках Netlify нельзя достоверно установить из публичного HTML: доступ к панели/API управления не использовался.

Имена с хэшами выше — журнал фактической проверки существующей публикации, **не настройки диагностической страницы**. Новая страница получает имена заново из опубликованного `index.html` при каждом запуске.

Ответы Netlify дополнены асинхронным скриптом `/.netlify/scripts/hud?variant=public`. Он отсутствует в локальном исходнике и не нужен для первого рендера меню. Его загрузка может влиять на индикатор загрузки браузера, однако причиной белого React root в нашей проверке он не стал. Новых аналитических сервисов в проект не добавлено.

## Как запускается приложение

`index.html` загружает один основной модуль Vite и один CSS-файл с собственного домена. Код React и меню входит в основной JS; загрузка не разделена на отдельный небольшой пакет только для меню. CSS, локальные WebP-фоны и рубашка карты оформляют меню. Внешних шрифтов или CDN-библиотек для первого экрана нет. Все локальные URL из собранного CSS проверены на наличие соответствующих файлов в `dist`.

`AppShell` сразу выбирает `MainMenu` для `/`. `ProfileProvider` синхронно читает гостевой профиль, а включение TTS лишь меняет настройку. Запрос озвучки запускается при действии пользователя. Worker/API и WebSocket используются только в соответствующих сценариях комнаты; их доступность не является условием отображения главного меню. Блокировка фонового изображения отдельно проверена: меню продолжает отрисовываться.

Ранее `#root` был пустым до запуска React. Отказ загрузки JS, ошибка его исполнения либо ранняя ошибка рендера оставляли пользователя без сообщения. В исходнике есть реальная точка несовместимости со старыми браузерами: новый профиль вызывает `crypto.randomUUID()`; отсутствие этого API может сорвать начальный рендер. Для российского браузера такая причина пока **не подтверждена**. Диагностика показывает поддержку API, а ошибка рендера теперь перехватывается.

Регистрация service worker и обращения к внешним сервисам шрифтов в проекте не найдены.

## Вероятные причины, пока без окончательного вывода

1. Основной JS или CSS не завершается на конкретной сети/устройстве: тайм-аут, обрыв, фильтрация или проблема доставки через CDN. Успешный маленький HTML доказывает доступность этого HTML, но не успешную загрузку остальных файлов. Из имеющихся данных нельзя объявить причиной блокировку Netlify, DPI или конкретного провайдера.
2. Ошибка исполнения в конкретном браузере: отключённый JavaScript, неподдерживаемый синтаксис/API, расширение или встроенный браузер. Нужны версия браузера и результат запуска.
3. Смешение кэшированных версий HTML и ресурсов либо ответ HTML вместо JS/CSS. В проверенной текущей публикации пути и MIME корректны; на проблемном устройстве это проверит новая страница.

Гипотеза «меню ждёт Cloudflare Worker/TTS/WebSocket» проверкой кода и запросов не подтверждается.

## Что добавлено

- `public/diagnostics.html`: сразу видимый обычный HTML, встроенный CSS и классический JavaScript без React/внешних библиотек. Последовательно запрашивает свежий `/index.html`, найденный основной JS, найденный CSS, фон из CSS-переменной `--table-art`, затем метаданные сборки. Для каждого запроса: результат, HTTP, размер тела после HTTP-декодирования и длительность. Тайм-аут каждого запроса — 12 секунд. MIME и подмена JS/CSS HTML-страницей распознаются. Основной JS при этих проверках **не исполняется**.
- Отдельная кнопка «Проверить запуск приложения» открывает только `/` в iframe и ждёт безопасного подтверждения React. Проверка не создаёт комнату и не требует Worker. Максимум ожидания — 15 секунд.
- `index.html`: доступное без React сообщение загрузки, ссылка на диагностику, сообщение при отключённом JS; глобальные обработчики ошибок ресурса, исполнения и необработанных Promise до успешного запуска; тайм-аут запуска 12 секунд. Успешный рендер скрывает панель, поздняя успешная загрузка также может убрать тайм-аут.
- `src/StartupBoundary.tsx`, `src/main.tsx`: граница ошибок React и подтверждение успешного рендера. При сбое показывается HTML-fallback. Тексты исключений, stack, состояние игры, параметры URL и содержимое хранилищ не выводятся и не отправляются. Отчёт в iframe содержит только фиксированный статус и безопасный код.
- `scripts/build.mjs`: после штатной сборки создаёт `dist/build-info.json`. В нём только публичные branch/commit, идентификатор сборки, источник метаданных, признак незакоммиченных изменений, время, имена/размеры/SHA-256 основных ресурсов. Для Netlify используются `BRANCH`, `COMMIT_REF`, `NETLIFY`; полного вывода окружения нет. При отсутствии Git сведения не выдумываются.
- `scripts/check-diagnostics.mjs`: воспроизводимая проверка production-сборки и диагностических сценариев.

Параметр `base: '/'` корректен для корневого домена Netlify. Vite копирует обе статические страницы из `public` в `dist`; диагностическая страница не зависит от SPA-редиректа. Конфигурация Worker и маршруты игры не менялись.

Локальный endpoint из игнорируемой `.env.local` нельзя переносить в настройки production: сохранить существующее production значение `VITE_ROOM_API_BASE`.

## Что попросить российского пользователя

После публикации открыть **диагностику, без ссылки на комнату**, дождаться окончания таблицы (в худшем случае около минуты), затем нажать «Проверить запуск приложения» и подождать до 15 секунд.

Прислать:

1. Скриншот всей таблицы: пути, результаты, HTTP, байты, время.
2. Блок «Сборка и возможности браузера», включая branch/commit и версию браузера.
3. Сообщение под кнопкой запуска и видимое окно приложения.
4. Устройство/ОС, оператор или сеть, наличие VPN и время проверки. При возможности сравнить Wi-Fi и мобильный интернет.

Не присылать HAR, данные localStorage, секреты восстановления, токены или приватные ссылки комнат. Для проверки кэша достаточно отдельного приватного окна/перезагрузки с обходом кэша; **очищать локальные сохранения и коды восстановления не требуется**.

Интерпретация: HTTP 0/тайм-аут указывает на отсутствие завершённого ответа, но сам по себе не доказывает блокировку; 404 — на отсутствующий ресурс/версию публикации; HTML вместо JS/CSS — на неверный ответ хостинга/перенаправления; все файлы 200 + ошибка запуска — повод проверить API/версию браузера и код fallback. Точную причину российского сбоя следует устанавливать по этим результатам, а не по успешному `/health.html`.
