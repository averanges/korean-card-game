# Независимая проверка Render

Это **не сервер Hangul Durak**. Здесь нет комнат, рук, словарей, авторизации и импорта игровых модулей. Существующие Worker, Pages, Vite и настройки игры не меняются. Новый сервер никак не подставляется в `VITE_ROOM_API_BASE`.

## Локальный запуск

Нужен Node.js 22 и npm. Из корня репозитория в PowerShell:

```powershell
Set-Location render-probe
npm ci
npm test
npm start
```

Открыть `http://localhost:10000/`. Если порт занят, перед запуском установить `$env:PORT = '10008'`. Сервер слушает `0.0.0.0` и `PORT`, как требуется Render. На локальной машине это также делает его доступным в вашей сети при разрешении брандмауэра.

## Подготовленная конфигурация Render — без публикации

В корне репозитория добавлен `render.yaml` для **отдельного нового** Free Web Service `hangul-durak-connectivity-probe`. Ничего на Render ещё не создано.

Настройки для ручного создания, **только после разрешения публикации**:

| Поле | Значение |
| --- | --- |
| Repository / branch | `averanges/korean-card-game` / `multiplayer` |
| Runtime | Node |
| Root Directory | `render-probe` |
| Build Command | `npm ci --omit=dev` |
| Start Command | `npm start` |
| Plan | Free |
| Region | Frankfurt |
| Health Check Path | `/health` |
| Environment | `NODE_VERSION=22` |
| Auto deploy | Off |

Frankfurt — исходная точка эксперимента, не доказательство оптимальной задержки для двух стран. Регион сервиса нельзя сменить после создания; для сравнения с Singapore потребуется отдельный сервис и отдельное разрешение. Порт Render назначает сам. Базу данных, секреты, домен игры и переменные Worker подключать не нужно.

Можно использовать Blueprint из корневого `render.yaml`. **Создание Blueprint запускает первое развёртывание даже при `autoDeployTrigger: off`**. Не создавать его до согласования. Имя должно принадлежать новому сервису, а не совпадать с существующим управляемым сервисом. Текущие файлы также не закоммичены и не отправлены в GitHub.

## Endpoint и диагностика

- `GET /health`: JSON `ok`, идентификатор тестового сервиса, версия диагностики, случайный `instanceId` процесса и его время работы. `Cache-Control: no-store`.
- `/ws`: обычный WebSocket; первым сообщением приходит `{type:"ready",instanceId,version:1}`. Запрос `{type:"ping",id:1}` получает `{type:"pong",id:1}`. Это **тестовый протокол**, не игровой.
- `/` и `/diagnostics.html`: самостоятельный HTML без React, внешних библиотек и запросов в Cloudflare.
- `/diagnostics.js`: локальный скрипт страницы.

Страница проверяет HTTP и затем WebSocket **даже при ошибке HTTP**. Измеряет HTTP-статус, количество байт, полное время HTTP, время открытия WS и готовности приложения, четыре RTT с интервалом 10 секунд (наблюдение около 30 секунд). Лимит на HTTP, включая чтение тела, — 90 секунд. Отдельный лимит на открытие WS/ready — 90 секунд; на каждый pong — 8 секунд. Закрывает соединение после проверки. Фоновый мониторинг и искусственное поддержание сервиса активным отсутствуют.

HTML-страница запуска Render вместо JSON считается ошибкой, даже если имеет статус 200. Браузер часто не позволяет отличить DNS, TLS, CORS и блокировку провайдером; диагностика честно сообщает эту неопределённость, а не называет любую ошибку блокировкой.

Тестовые данные публичны, поэтому HTTP использует `Access-Control-Allow-Origin: *` без cookies/credentials. WS доступен в том числе из локального файла с Origin `null`. Это позволяет независимую проверку из разных браузеров. **Не переносить такую открытую политику на будущие комнаты**. Сервер принимает только маленькие ping-сообщения, ограничивает размер (1 КиБ), число сообщений (50), число сокетов (100), время соединения (120 секунд), не отражает произвольный текст и не записывает содержимое сообщений/IP в прикладные логи. Инфраструктура Render может иметь свои технические логи.

## Проверка после разрешённой публикации

Фактический URL будет назначен Render. Далее обозначен как `https://SERVICE.onrender.com`; это **шаблон, а не опубликованный адрес**.

1. Проверяющие в России и Корее открывают `https://SERVICE.onrender.com/health`, затем `/diagnostics.html`.
2. Выбирают страну и сеть, нажимают проверку и скачивают JSON-отчёт. В нём нет имён, секретов комнат, IP, токенов или произвольных параметров URL.
3. Если Render-страница вообще не загружается: передать пользователю **оба файла** `public/diagnostics.html` и `public/diagnostics.js` в одной папке. Открыть HTML локально и ввести корневой HTTPS-адрес сервера. Если телефон не позволяет исполнять локальные скрипты, использовать настольный браузер; можно также отдельно открыть `/health` и прислать скриншот ошибки загрузки страницы.
4. Сделать три обычных прогона. Сравнить домашнюю/мобильную сеть, при необходимости отдельно с VPN и без. Не смешивать эти результаты.
5. Повторить после более 15 минут без проверок/пользовательских запросов для наблюдения холодного старта. Это не гарантирует засыпание: состояние платформы и проверки могут влиять на эксперимент. После первого долгого подключения сделать повторный тёплый прогон.
6. Во время отдельного прогона отключить/включить сеть или отправить браузер в фон: ожидается сообщение об обрыве/тайм-ауте, затем ручной повтор. Диагностика не имитирует восстановление комнаты.
7. После перезапуска/повторного развёртывания (только с разрешения) сравнить `instanceId`. Его смена показывает новый процесс. Состояния комнат в этом эксперименте нет.

Прислать отчёты с обоих направлений, сеть, факт VPN, примерное время и ошибку загрузки HTML, если она возникла. Даже четыре успешных pong — только краткая проверка транспорта, не гарантия стабильности длинной партии. К переносу переходить после повторяемого успеха HTTP, WS и наблюдения холодного старта в обеих странах. Не считать местный localhost доказательством доступности Render из России.

## Ограничения бесплатного Render

Проверено по официальной документации 20.10.2026:

- После 15 минут без входящего HTTP/сообщений WebSocket сервис засыпает. Новое HTTP/WS-подключение запускает его; пробуждение занимает около минуты. Наличие молчащего сокета само по себе не заменяет входящие сообщения.
- Доступно 750 бесплатных часов на workspace в месяц, общий бюджет для Free Web Services. Исчерпание приостанавливает сервисы до следующего месяца. Также действуют лимиты исходящего трафика и сборок.
- Память процесса теряется при перезапуске/засыпании/новой версии. Локальная файловая система тоже временная: JSON-файл или SQLite в каталоге сервиса **не сохраняют комнаты**. Бесплатному Web Service нельзя подключить постоянный диск.
- Render может перезапустить Free-сервис в любой момент. Один экземпляр, масштабирование недоступно. Сокеты при остановке обрываются.
- Бесплатный Postgres истекает через 30 дней; Free Key Value теряет данные при перезапуске. Они не дают бессрочной надёжности комнат и персональных кодов.
- Официально Free рекомендован для экспериментов, а не production. Даже платный постоянно работающий процесс требует долговечного хранилища для восстановления после сбоя.

Текущий игровой клиент ожидает ответ API за 12 секунд, а авторизацию сокета — за 12 секунд. Это существенно короче холодного старта Free Render. Для будущего переноса потребуется отдельный экран/стадия пробуждения и управляемые тайм-ауты; **сейчас клиент не меняется**. Не обходить засыпание внешними keep-alive-сервисами ради эксперимента.

Источники: [Free](https://render.com/docs/free), [WebSocket](https://render.com/docs/websocket), [Blueprint](https://render.com/docs/blueprint-spec), [Node version](https://render.com/docs/node-version).

## Условный план переноса после успешных региональных тестов

1. Зафиксировать контракт из `src/rooms/protocol.ts`: create/join/recover, первое auth-сообщение с секретом, снимки, command result, ревизии, события и коды закрытия. Написать контрактные тесты обоих транспортов; текущий Worker оставить доступным.
2. Выделить общий серверный слой из `worker/src/model.ts`, `gameSession.ts`, `magicSession.ts`, сохранив их поведение. Максимально переиспользовать `src/game-core`, `engine.ts`, `learning.ts`, `gameFactory.ts`, магию и проекции. Node.js 22 поддерживает используемые Web Crypto/structuredClone; проверить сборку и типы отдельно. `cloudflare:workers`, `DurableObject`, хранилище, alarms, WebSocketPair, auto-response и attachments заменить адаптерами, не писать правила заново.
3. Сделать Node HTTP/WS-адаптер с теми же схемами, ограничениями размера/частоты, allowlist Origin, сроком авторизации и TTL. Секреты только в теле HTTPS/первом WS-кадре, никогда в URL/логах; сравнения и хранение хешей, детерминированная модель восстановления и персональные коды сохраняются. Имя и приглашение не дают право занять чужое место.
4. **До тестовых реальных партий** выбрать долговечное хранилище. Транзакционно сохранять весь `StoredRoom`: игру, руки, остаток пула, эффекты и длительности, учебные задания, счётчики наград, секретные данные модели, ревизии, TTL и дедупликацию requestId. Закрытые поля и правильные ответы не отправлять сопернику. Снимки строить через существующие `sessionSnapshot`/проекции отдельно для каждого игрока; сервер — единственный источник истины.
5. Сохранить сериализацию команд на комнату, атомарное обновление состояния и idempotency. Для единственного процесса очередь достаточна только вместе с транзакцией; при будущих нескольких экземплярах понадобятся блокировки/владелец комнаты и маршрутизация или pub/sub. Не заменять Durable Objects простым Map без оговорки о потере состояния.
6. Реализовать восстановление сокета с heartbeat/backoff, актуальным PlayerView, незавершённым заданием и прежней политикой однократной безопасной замены соединения. После рестарта сбрасывать устаревшие connectionId, но сохранять места и партию. TTL выполнять таймером/очисткой в БД и при обращении, чтобы рестарт не отменял истечение комнаты.
7. Проверить две настоящие клиентские сессии: все обычные/магические действия, повторы команд, скрытые/слепые карты, награды, восстановление во время задания, авторизацию, перезапуск между командами, занятую комнату, старые секреты, холодный старт и краткий сетевой обрыв. Одиночный режим остаётся на прежнем движке.
8. Подключать новый API только в отдельной тестовой сборке через существующий `VITE_ROOM_API_BASE`, после разрешения. Предусмотреть откат на Worker. Перенос живых комнат между платформами — отдельная задача экспорта, шифрования и миграции, а не автоматический результат смены URL.

Этот план не реализован на первом этапе. Выбор Render вместо Cloudflare пока не подтверждён региональными измерениями.
