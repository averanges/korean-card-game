# Этап 3B-1 — серверная магия и учебные задания

Семь существующих типов магических карт подключены к сетевой партии. Этап реализован локально в ветке `multiplayer`, поверх оставшихся незакоммиченных изменений этапа 3A. Push, merge и deploy не выполнялись. Одиночный режим, стратегия бота, изображения карт и баланс не менялись. Художественная интеграция магических окон и анимаций остаётся этапом 3B-2.

- `src/rooms/MagicTestPanel.tsx` — минимальная текстовая панель для проверки реального протокола.
- `worker/test/magicSession.test.ts` — выдача, конечный пул, права обоих мест, все семь эффектов, отмена, сгорание, дополнительные цели и слепые ссылки.

## 2. Создание игры и выдача

Новые комнаты по умолчанию создают магическую партию через существующий `createGame` с серверным источником случайности. Режим задаёт Worker-переменная `NETWORK_GAME_MODE`:

- `magic` — новый режим по умолчанию;
- `ordinary` — сохранённый режим этапа 3A, используемый также регрессионными тестами.

Клиент не может подменить этот параметр в HTTP или WebSocket-команде.

Начальная раздача содержит по шесть обычных карт и ни одной магической. При обычном доборе движок сам вызывает исходный `rollMagicDrop`, с теми же вероятностями, весами и штрафом за повторное выпадение. Сохраняется физический пул из 11 экземпляров: три уникальных легендарных и по два остальных типов. Выданный экземпляр удаляется из пула, использованный или сгоревший не возвращается в него.

В полном состоянии движок по-прежнему использует свою существующую структуру рук. В `PlayerView` обычные карты и собственная магическая экстра-рука разделены на `hand` и `magic`; при доборе до шести считаются только обычные карты. Отдельная система выпадения не создавалась.

## 3. Команды WebSocket

Используется прежний конверт с `v: 1`, `type: "command"` и `command`, содержащей `requestId` и `expectedRevision`.

| Команда | Дополнительные поля |
| --- | --- |
| `begin_magic` | `magicRef` — своя магическая карта |
| `answer_quiz` | `challengeId`, `option` — индекс 0–3 |
| `cancel_quiz` | `challengeId` |
| `choose_trump` | `challengeId`, `trump` — масть 0–3 |
| `choose_hat_card` | `challengeId`, `cardRef` — своя допустимая карта |

Сохраняются обычные команды этапа 3A. Лишние поля запрещены, в том числе `correct`, клиентское состояние и случайные индексы. Автор игрока определяется только по подтверждённому socket.

Начать магию можно в своей разрешённой атаке или незавершённой защите. Ожидающий защитник без атакующего стола и защитник уже полностью отбитого стола не могут открыть задание. Дополнительно применяется существующий `magicUnavailable`. В слепой атаке сначала требуется выбрать закрытую карту.

## 4. Хранение попыток и транзакции

Схема 3 хранит:

- полную игру, руки, оставшийся пул и эффекты;
- `ChallengeBook`, текущую попытку каждого места и историю `usedIds`;
- фазу `question` / `target` / `resolved` / `cancelled` и результат попытки;
- последние слова заданий для исключения частых повторов;
- сериализованные карты непрозрачных ссылок, раунды, порядок закрытых карт и подписи актуальности руки;
- `gameRevision` и прежние квитанции `request:<seat>:<requestId>` в Storage.

Важные данные не остаются только в памяти экземпляра. Вопрос, правильный ответ и обязательный выбор сохраняются вместе с состоянием партии и квитанцией команды одной транзакцией. Подтверждение и рассылка выполняются после её завершения. Сбой после записи, но до фиксации проверен настоящей SQLite-транзакцией: вопрос остаётся открытым, карта не расходуется.

Повтор успешного `requestId` возвращает прежнюю квитанцию и текущий снимок. Повтор ответа с новым ID после завершения попытки отклоняется. Старый `challengeId` не становится новой попыткой. Ревизии проверяются и для вопросов, и для дополнительных выборов.

Открытие вопроса карту не расходует. Отмена до ответа завершает попытку и оставляет карту. Неверный ответ расходует её ровно один раз без эффекта. Правильный ответ применяет эффект или переводит попытку в обязательный выбор. После ответа отмена запрещена.

Пока собственная попытка находится в `question` или `target`, обычные команды этого игрока отклоняются. Второй игрок продолжает выполнять свои законные действия. Глобальной паузы нет.

После каждого подтверждённого перехода проверяется, остались ли незавершённые эффекты применимыми. Потерявшая применимость попытка атомарно становится `resolved / unavailable`, её карта сохраняется, владелец получает обновление. Это предотвращает зависание, например когда у Шляпы исчезли все допустимые цели. Если недопустима только выбранная цель, а другие ещё есть, попытка остаётся в `target` и можно выбрать снова без второго вопроса.

## 5. Вопросы и дополнительные выборы

Задания создают исходные `makeMagicQuiz` и `beginMagicChallenge`; проверяют `answerMagicChallenge` и `chooseMagicTarget`. Оба направления вопросов сохранены. У отправляемого вопроса ровно четыре варианта из актуального словаря партии и один правильный ответ.

Только владелец получает `game.challenge`: ID, свою магическую карту, фазу и публичный вопрос `{challengeId, direction, prompt, options}`. Поля `correct`, `index`, полный словарь и внутренний `ChallengeBook` не отправляются даже владельцу. Соперник не получает чужой вопрос или ответ.

После правильного ответа:

- Переворот судьбы передаёт владельцу три допустимые другие масти. Сервер проверяет выбранную относительно текущего козыря и применяет существующий переход. Эффект сохраняет исходную длительность.
- Шляпа передаёт только допустимые идентификаторы собственных доступных карт через `hatTargets`. Сервер выбирает реальный экземпляр из колоды со строго более высоким номиналом, переносит старую карту в сброс и отдаёт новую владельцу. Инверсия Зеркального мира не меняет сравнение номиналов Шляпы.
- Для Призрачного вора и прочих случайных результатов используется серверный генератор. Клиент не выбирает случайный индекс.

## 6. Скрытые карты и Обезьянья проделка

Полная партия не отправляется клиенту. Снимки проходят через `projectGameForPlayer`, события — через `projectEventsForPlayer`.

Публично синхронизируются число магических карт, эффекты и их длительность, козырь, инверсия, остаток колоды, блокировки и фаза. Содержимое чужих рук и пула остаётся закрытым. Событие Подарка раскрывает полученную обычную карту только получателю. Новая карта Шляпы раскрывается только владельцу. Сбрасываемая Шляпой старая карта отражается существующей публичной проекцией события.

Для Обезьяньей проделки:

1. При начале соответствующей атаки создаётся `ProjectionContext` с непрозрачными UUID-ссылками.
2. Сервер отдельно перемешивает порядок отображения. Реальный порядок и содержимое руки не меняются.
3. Клиент получает только `{ref, hidden: true}`. Даже `allowed.attack` содержит ссылки, а не реальные ID.
4. Команда разрешает выбранную ссылку через `resolveBlindReference`, после чего настоящий движок разыгрывает одну карту.
5. Разыгранная карта становится публичной, подкидывания запрещаются существующим эффектом.
6. При изменении руки, доступных карт, раунда или завершении эффекта ссылки обновляются либо удаляются. Старая ссылка не может сыграть другую карту.

Контекст, перемешанный порядок и подписи сохраняются до рассылки. Переподключение и hibernation восстанавливают тот же актуальный набор ссылок. В закрытом состоянии также скрываются лица обычного добора и освобождаемой заблокированной карты в событиях: они не должны раскрывать руку обходным путём.

## 7. Миграция и ограничения

Комнаты схемы 2 мигрируют при загрузке на схему 3, без новой раздачи и без изменения `gameRevision`. Уже начатая обычная партия 3A остаётся обычной, её колода и руки не меняются. Магия включается в новых партиях. Для проверки создайте новую комнату; повторная раздача в той же завершённой комнате по-прежнему не предусмотрена.

Wrangler migration `v1`, binding и политика TTL сохранены. При окончательном истечении очищаются игра, задания, контекст ссылок и история вопросов; затем Storage удаляется по прежней политике.

Секрет восстановления по-прежнему хранится в `sessionStorage`. Закрытие или очистка браузерной сессии может лишить игрока возможности вернуть место. Временное отключение или обновление вкладки не сбрасывает вопрос и не даёт вторую попытку.

Панель намеренно проверочная: текст и обычные кнопки, без художественных магических окон, новых изображений и специальных магических анимаций. Ручная визуальная проверка двух браузеров в изолированной среде не подтверждена; её шаги приведены ниже. Серверные сценарии выполнялись через настоящие WebSocket и workerd, а не моки.

- Обе разновидности вопросов, четыре уникальных варианта, отмена, правильный и неправильный ответы, запрет второго ответа и подмены результата.
- Все семь эффектов, дополнительные цели, повтор выбора, скрытый Подарок, номинал Шляпы, истечение Призрачного вора, слепые ссылки и запрет подкидываний.
- Действие соперника во время вопроса и исчезновение применимости, в том числе во время обязательного выбора Шляпы.
- Реальные hibernation и полный перезапуск runtime с открытым вопросом, обязательным выбором и слепой рукой.
- Ответ, подтверждение которого намеренно не прочитано владельцем, с переподключением и повтором того же запроса без повторного расходования.

- Проверка фактического JSON сообщений на правильный индекс, закрытые карты, внутренние ссылки и ключи состояния.

Для воспроизводимой проверки всех семи типов интеграционный тест готовит физические карты в изолированных тестовых модулях, сохраняя 36 обычных и 11 магических экземпляров. В production-исходниках нет команды выдачи карт или обхода учебной проверки. Отдельный полный сценарий магического режима работает с обычной серверной раздачей и шансами.

## 9. Ручная проверка в двух браузерах

Запуск из корня проекта, как на предыдущем этапе (Node.js 22+):

```powershell
npm ci
# Если .env.local ещё нет:
Copy-Item .env.example .env.local
npm run dev
```

Во втором PowerShell, из корня проекта:

```powershell
Set-Location worker
npm ci
npm run dev
```

В `.env.local` нужен публичный `VITE_ROOM_API_BASE=http://127.0.0.1:8787`. Worker по умолчанию настроен на `NETWORK_GAME_MODE: "magic"`.

1. В браузере A откройте `http://localhost:5173/multiplayer`, создайте новую комнату.
2. Откройте приглашение в браузере B или приватном окне, присоединитесь и начните игру у создателя.
3. Проведите несколько раундов с обычным добором. В начальной раздаче магии нет; выпадение случайное, нужная карта может не прийти в одной партии.
4. Раскройте слева «Магия · проверочная панель». Там видны только собственные магические карты и число карт соперника.
5. В разрешённую атаку или защиту нажмите активацию. Проверьте, что карта остаётся в руке, а вопрос виден только владельцу. До ответа попробуйте отменить.
6. Откройте снова и дайте неправильный ответ: карта должна сгореть без эффекта. Для следующей карты дайте правильный ответ и проверьте публичное изменение.
7. Для Переворота судьбы выберите другую масть. Для Шляпы выберите один из предложенных собственных номиналов. После ответа отмены нет.
8. При открытом вопросе обновите вкладку. Вопрос, варианты и ID попытки должны сохраниться. Можно также перезапустить локальный Worker без удаления `.wrangler` и вернуться в оба браузера.
9. Во время вопроса выполните законное действие соперником. Если оно лишило эффект применимости, владелец увидит «Эффект больше недоступен. Карта сохранена».
10. После Обезьяньей проделки дождитесь атаки проклятого игрока. Внизу появятся только закрытые варианты `✧`. Выбранная карта раскроется на столе; подкидывание в этом эпизоде недоступно.

Для гарантированной проверки редких карт и всех сценариев без ожидания выпадения:

```powershell
Set-Location worker
npm run check
npm test
```

Публикация и визуальная интеграция 3B-2 требуют отдельного задания.
