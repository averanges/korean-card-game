# Мобильная компоновка: локальная и опубликованная сборки

Проверка 19 октября 2026. Ветка `multiplayer`. Push, merge, deploy, git add и commit не выполнялись.

## Установленная причина

На Pages опубликована сборка **до этапа 5**, тогда как предыдущий отчёт описывал локальные незакоммиченные изменения. Сравнения опубликованного домена в той проверке не было. Теперь расхождение проверено непосредственно на сайте и на настоящих локальных партиях.

Последний локальный коммит `ea6cbd2 Optimize assets and mobile gameplay layout` фактически меняет **только две строки в `worker/test/decks.integration.test.ts`**. Ни мобильная раскладка, ни оптимизированные изображения в него не попали. `git show HEAD:src/main.tsx` показывает прежний вход без `MobileHud`, а `src/MobileHud.tsx`, `src/useCompactViewport.ts`, `src/mobile.css` и новые WebP остаются незакоммиченными. Индекс Git пуст.

Поэтому повторная сборка этого коммита в Pages снова создаст прежний интерфейс. Название коммита не подтверждает его содержимое.

## Диагностика viewport, CSS и inline-геометрии

1. На опубликованном сайте уже есть корректный `width=device-width, initial-scale=1.0`; Chrome действительно сообщает `innerWidth=390`. Это не ошибка отсутствующего viewport. Локальный HTML дополнительно содержит `viewport-fit=cover`.
2. Локальная мобильная граница — `(max-width:600px), (max-width:1000px) and (max-height:500px)`. При 390×844 и 360×780 она возвращает `true`.
3. В локальном приложении `useCompactViewport` используется и одиночным `App`, и `NetworkTable`; они получают `compact-layout` и создают общий `MobileHud`. Большая `statusbar` и `bot-hand` при этом вообще не создаются в DOM.
4. `mobile.css` подключён после остальных игровых стилей. Вычисленные стили подтверждают Grid, относительные позиции и мобильные размеры. Позднего настольного переопределения в локальной сборке нет.
5. `OrdinaryHand` и `BlindHand` передают мобильный режим в `handLayout`: шаг 110 px при ширине карты 100 px, угол 0. Реальные inline-transform имеют вид `matrix(1, 0, 0, 1, x, 28)`; старое вращение веера не сохраняется.
6. На опубликованном сайте JS без этой ветки продолжает создавать настольные узлы, а CSS без `compact-layout` использует прежние телефонные уменьшения настольного оформления. Поэтому остаются большой веер, перекрытия руки и действия справа. Добавление новых CSS-переопределений к уже правильной локальной версии здесь не требуется.

## Проверка настоящих партий

Использована свежая production-сборка Vite, не `mobile-fixture.html` и не отдельный тестовый компонент. Для сетевого режима запущен настоящий исходный Worker в локальном Miniflare с Durable Object, **без подстановки рук, снимков или тестовой магии**. Два независимых браузерных контекста создали комнату через интерфейс, подключились по WebSocket, начали игру и выполнили разрешённые сервером атаки, защиту и подкидывание через реальные кнопки. Команды и состояние не подменялись. Публичный Worker для этого не использовался; опубликованные комнаты не создавались.

Одиночный режим открыт через `/singleplayer`, ходы выполнены настоящими кнопками против существующего бота с обычными браузерными таймерами. Для снимка первой атаки тест дожидается окончания входной анимации и проверяет, что на столе ровно одна карта; для следующего снимка требует минимум две. Правила, React-состояние и часы не подменяются. В отчёт сохраняется геометрия, а не секреты восстановления и не снимки закрытых рук.

## Что требуется для публикации

Нужен **новый полный commit и push** после просмотра изменений; повторный deploy нынешнего `ea6cbd2` и очистка браузерного кэша недостаточны. Эти действия здесь не выполнены.

1. Просмотреть `git status --short` и `git diff --stat`. Добавить в будущий коммит и изменённые отслеживаемые файлы, и новые компоненты/CSS, и WebP, сохранив предусмотренный перенос исходных PNG в `design/source-assets/`. Команда, включающая только ранее отслеживаемые изменения, пропустит новые файлы. Не добавлять `dist`, `node_modules`, `.env*` или `work`.
2. Убедиться, что будущий коммит содержит `src/MobileHud.tsx`, `src/useCompactViewport.ts`, `src/mobile.css`, их подключения в обоих столах и `public/assets/*.webp`. Само имя коммита не является проверкой.
3. Выполнить `npm run build`, затем `node scripts/check-mobile-build.mjs`. После создания полного коммита выполнить также `node scripts/check-mobile-build.mjs --git-head`.
4. Когда будет отдельно разрешён push, отправить полный коммит. В Pages проверить проект, каталог проекта, ветку `multiplayer`, SHA нового коммита и успешную сборку: `npm run build`, выход `dist`. Настройки ветки и SHA внутри аккаунта Cloudflare здесь не проверялись; публичная версия и локальный Git проверены непосредственно.
5. Сохранить production-переменную `VITE_ROOM_API_BASE` с публичным адресом существующего Worker. Локальная проверка использует `127.0.0.1:8787`; этот локальный адрес нельзя переносить в production-настройки Pages. Сервер заново публиковать для этой раскладки не требуется.

## Проверка Android после согласованной публикации

Сначала убедиться, что HTML домена ссылается на JS/CSS **новой** сборки и загруженный CSS содержит `.compact-layout` и `.mobile-hud`. Имена хэшей могут измениться из-за production-переменных; обязательны новые компоненты и правила, а не буквальное совпадение локального JS-хэша.

На Android открыть новую вкладку или обновить страницу. Через Chrome Remote Debugging проверить `window.innerWidth`, `matchMedia('(max-width:600px)').matches`, класс `compact-layout` у игрового `main`, наличие `.mobile-hud` и отсутствие `.bot-hand`. У руки должны быть `overflow-x:auto`, нулевой угол карт и заметные промежутки между ними.

Начать одиночную и сетевую партии, сделать первую атаку, отбить её и подкинуть ещё карту. Сравнить с приложенными настоящими скриншотами: небольшой HUD, стол в две колонки, кнопки над горизонтальной рукой. Прокрутить руку до последней карты, проверить выбор и отсутствие случайного хода при свайпе; повернуть телефон и вернуться в портрет.

Если снова видны большой веер и кнопки справа, сначала посмотреть загруженные имена JS/CSS и SHA deployment. Старые `index-CaQuA0xu.js` / `index-DuQLSZaG.css` означают, что домен всё ещё обслуживает прежнюю сборку. Удаление данных сайта не требуется как первый шаг: оно может удалить локальное восстановление комнаты. Очистку кэша имеет смысл проверять только после подтверждения, что сам домен уже отдаёт новую версию.
