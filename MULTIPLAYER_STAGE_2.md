# Этап 2: приватные комнаты

Реализованы комнаты для двух участников, сохранение мест, WebSocket и восстановление соединений. Сетевая партия намеренно не запускается. `/` по-прежнему открывает одиночную игру с ботом; `/multiplayer` — создание комнаты; `/room/ID` — вход или восстановление места. Колода при открытии комнаты не создаётся.

## Структура

- `worker/src/index.ts` — Worker, проверка Origin и запросов, Durable Object `Room`, hibernation WebSocket API, Storage и Alarms.
- `worker/src/model.ts` — сохраняемая модель комнаты, авторизация мест и публичная проекция.
- `src/rooms/protocol.ts` — общий протокол v1 и проверка клиентских команд.
- `src/rooms/RoomLobby.tsx`, `connection.ts`, `room.css` — отдельный экран, сессия и reconnect.
- `worker/wrangler.jsonc` — binding `ROOMS`, SQLite migration `v1`, локальные адреса и TTL.
- `public/_redirects` — SPA-маршруты для Pages, включая обновление страницы комнаты.

Правила, бот, учебные задания и анимации одиночной игры не изменялись на этом этапе. Сервер не импортирует React, TTS или бота. Подготовленное `src/game-core` потребуется при добавлении сетевых игровых команд на следующем этапе.

## Запуск в обычном Windows PowerShell

Нужен Node.js **22 или новее** (рекомендуется актуальный LTS). Frontend и Worker устанавливаются отдельно, у каждого свой lockfile.

Из корня проекта:

```powershell
npm ci
Copy-Item .env.example .env.local
npm run dev
```

Во втором окне, из корня проекта:

```powershell
Set-Location worker
npm ci
npm run dev
```

Frontend: `http://127.0.0.1:5173/multiplayer` или `http://localhost:5173/multiplayer`. Worker: `http://127.0.0.1:8787`. Обе локальные frontend-origin разрешены. Wrangler запускает локальный Durable Object, хранит данные под `worker/.wrangler/`; авторизация Cloudflare для локального запуска не требуется. Если порт Vite изменён, добавьте соответствующий точный Origin в конфигурацию Worker и обновите `FRONTEND_ORIGIN`.

Для ручной проверки откройте приглашение во втором браузере или приватном окне. Это отдельная браузерная сессия. Повторное открытие того же места заменяет старое соединение, поэтому две вкладки с одной сессией не являются двумя игроками.

Проверки из корня проекта:

```powershell
npm test
npm run build
Set-Location worker
npm run check
npm test
```

Worker-тесты используют настоящий локальный runtime Miniflare/workerd, SQLite и WebSocket, без аккаунта Cloudflare. Тестовый TypeScript временно компилируется в `.wrangler/test-build`; каталог игнорируется Git. Miniflare закреплён в lockfile; используется адаптер его API v4 в установленный v5.

## HTTP и WebSocket

- `POST /api/rooms` — JSON `{name, joinKey}`. Ответ: `{roomId, seat, recoverySecret, inviteUrl}`. ID и секреты имеют 256 бит энтропии.
- `POST /api/rooms/:id/join` — JSON `{name, joinKey}`. Выделяет второе место, либо возвращает прежнее при повторе того же `joinKey`. Третьему участнику — HTTP 409 `room_full`.
- `GET /api/rooms/:id/ws` — WebSocket upgrade с разрешённого Origin. Первое сообщение: `{v:1,type:"authenticate",secret:recoverySecret}`. Секрет никогда не передаётся в URL.
- После авторизации допустимо `{v:1,type:"get_snapshot"}`. Другие команды пока отклоняются. Любой присланный `playerId` запрещён строгой схемой.
- События: `room_snapshot`, `player_joined`, `player_left`, `player_reconnected`, `room_ready`, `error`. Снимок содержит `v`, `self` и публичную `room` с монотонной `version`. Публичные данные не включают recovery-секреты, хеши, seed, join proof и идентификаторы соединений.
- Автоматический heartbeat `ping` / `pong` поддерживает соединение без пробуждения hibernating DO. Он не продлевает TTL комнаты.

Состояние комнаты сохраняется до рассылки событий. Входящие операции сериализованы внутри DO. При пробуждении подключения восстанавливаются из attachments, при полном перезапуске сохраняются места и имена. Чужой секрет не позволяет выбрать другое место: сервер сам привязывает socket к найденному месту.

HTTP JSON ограничен 2 KiB; WebSocket-команда — 4 KiB. До авторизации даётся 10 секунд, максимум четыре ожидающих сокета на комнату. Ограничение команд — 30 за 10 секунд на соединение. Неизвестные команды и неверные данные не меняют состояние комнаты.

## Восстановление и хранение

`sessionStorage` хранит отдельный recovery-секрет каждой комнаты и случайный `joinKey`, необходимый для безопасного повтора входа после потерянного ответа. Приглашение содержит только ID комнаты. Имя не является авторизацией. Очистка хранилища или закрытие сессии браузера может лишить игрока возможности восстановить место; занятое место не выдаётся другому посетителю по одному приглашению.

Новое авторизованное соединение того же места закрывает старое с кодом 4009. Старый клиент прекращает reconnect, чтобы вкладки не вытесняли друг друга бесконечно. Обычный обрыв запускает до восьми попыток, задержка растёт от 0,5 до 15 секунд с небольшим случайным смещением. Повторная успешная авторизация сбрасывает счётчик. Есть ручное переподключение. Коды 4001 (авторизация), 4004 (истечение), 4009 (замена) останавливают автоматические повторы.

Повтор входа с тем же `joinKey` не создаёт третье место и не меняет имя. Создание комнаты при двойном отдельном POST может создать две разные комнаты; клиент блокирует двойное нажатие и не повторяет POST автоматически. Комната, ответ которой потерялся, очищается по TTL.

Настройки:

| Переменная Worker | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `WAITING_TTL_SECONDS` | 14400 | 4 часа после активности, пока второй участник не занял место |
| `ROOM_TTL_SECONDS` | 86400 | 24 часа после активности в комнате с двумя выделенными местами |
| `EXPIRED_RETENTION_SECONDS` | 3600 | час хранения отметки об истечении, затем полное удаление |

Отключение не освобождает место. Статус `ready` означает, что оба участника подключены; иначе `waiting`. Статусы `playing` и `finished` предусмотрены протоколом для следующего этапа. Alarm закрывает просроченные соединения и удаляет recovery-данные, затем удаляет запись комнаты. Нет фонового бесконечного перебора комнат.

## Публикация — отдельный шаг вручную

В этой задаче публикация не выполнялась. Не передавайте Cloudflare-токен в чат и не записывайте его в `VITE_*`.

1. В `worker/wrangler.jsonc` установите `FRONTEND_ORIGIN` в реальный HTTPS-адрес опубликованного Pages-сайта. `ALLOWED_ORIGINS` — список точных разрешённых frontend-origin через запятую, без `*`. При необходимости добавьте отдельно preview-домен. Локальные адреса в production можно убрать.
2. В обычном PowerShell, когда будете готовы публиковать Worker:

```powershell
Set-Location worker
npm ci
npm run check
npm test
npx wrangler login
npm run deploy
```

Wrangler создаст binding Durable Object согласно migration `v1`. В дальнейшем не удаляйте существующие migration tags; изменения оформляются новыми миграциями.

3. В настройках сборки Cloudflare Pages задайте **публичную** переменную `VITE_ROOM_API_BASE=https://<реальный-адрес-worker>`. Это базовый адрес Worker, без `/api`. Frontend на HTTPS должен обращаться к HTTPS Worker (WebSocket автоматически использует WSS).
4. Пересоберите Pages: команда `npm run build`, каталог результата `dist`, корень сборки — корень существующего React-проекта. Никакого серверного секрета в Pages не требуется. Добавление Worker не меняет способ статической сборки Pages.
5. Проверьте приглашение с двух устройств, обновление `/room/ID`, отключение сети и повторный вход. Корневая страница остаётся одиночной игрой.

Без `VITE_ROOM_API_BASE` экран комнаты объясняет, что сервер не настроен; одиночная игра продолжает работать.

## Выполненные проверки

Прошли проверки типов frontend и Worker, production-сборка frontend, все 43 существующих теста игры и семь новых тестов комнат. Интеграционный сценарий выполняет создание, host/guest-подключение, повтор входа, отказ третьему участнику, отказ неверному секрету, неверную/слишком большую команду без изменения версии, замену вкладки, обрыв и восстановление, принудительную hibernation с сохранением сокетов и полную перезагрузку runtime с восстановлением Storage.

В ограниченной среде Codex обычный Wrangler dev упёрся в права доступа к пользовательскому каталогу логов и чтению родительских каталогов при bundling. Проверки runtime выполнены через Miniflare с явно переданными скомпилированными модулями; это не удалённый deploy. Существующие 43 теста в этой среде запущены через временную компиляцию, поскольку установленный `tsx` не смог получить Windows userInfo. Обычные команды для пользовательского PowerShell приведены выше.

Полная ручная проверка интерфейса через встроенный браузер осталась неподтверждённой: локальный Vite dev остановился на ограничении доступа esbuild к родительским каталогам. Production-сборка проходит. Повторное открытие и восстановление места проверены на уровне реального HTTP/WebSocket-сценария; визуальный экран и копирование ссылки нужно дополнительно проверить в обычном браузере при локальном запуске.
