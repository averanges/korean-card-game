# Этап 3A — сетевая партия без магии

Реализована полная партия подкидного «Дурака» между двумя людьми в приватной комнате. Изменения локальные, в ветке `multiplayer`; push, merge и deploy не выполнялись. Магия в сетевом режиме отключена. Одиночный режим с ботом и семью магическими эффектами сохранён.

## Контроллер и хранение

`Room` остаётся единственным источником истины. Создатель может начать игру, только когда оба участника подключены. `worker/src/gameSession.ts` преобразует проверенную команду в `Action` существующего `engine.ts` и вызывает ядро. Второго движка правил нет.

`src/game-core/ordinary.ts` вызывает обычную раздачу `createGame` с серверным источником случайности `crypto.getRandomValues`, затем очищает `magicPool`. Поэтому ни начальная раздача, ни дальнейший добор не выдают магию. Обычные 36 карт, порядок добора, козырь, первый атакующий, старшинство, подкидывание, взятие и отбой определяются существующим движком. Сетевой протокол вообще не принимает команды магии.

Сохраняемая комната теперь имеет `schemaVersion: 2`, полное `game` и отдельную `gameRevision`. Старые комнаты без версии и игры продолжают работать как лобби. `room.version` изменяется также при подключениях; `gameRevision` изменяется только при подтверждённых игровых переходах. Обновление вкладки или изменение presence не сбрасывает раздачу и не меняет ревизию партии.

Каждый успешный ход записывается одной транзакцией Storage:

1. Новое состояние комнаты и партии.
2. Квитанция `request:<место>:<requestId>` с результатом и ревизией.
3. Следующий Alarm.

Лишь после завершения транзакции сервер меняет рабочую ссылку на состояние, подтверждает команду и рассылает представления. При ошибке транзакции неподтверждённый ход не рассылается; сервер перечитывает сохранённое состояние и возвращает `storage_error`. Тест проверяет реальный откат SQLite-транзакции после записей.

Повтор успешного `requestId` того же участника возвращает сохранённую квитанцию и актуальный снимок без повторного применения и анимаций. Квитанции сохраняются и после перезапуска runtime. Неверные команды не расходуют карты и не меняют игровую ревизию. Устаревший `expectedRevision` возвращает `stale_revision` и актуальный снимок.

TTL сохраняет политику этапа 2: до входа второго игрока — 4 часа без активности, после выделения обоих мест — 24 часа после последней активности, затем час хранения отметки об истечении. Подтверждённый игровой ход продлевает TTL. Краткое отключение не удаляет партию. При окончательном истечении очищаются игра и секреты, после периода хранения — вся Storage, включая квитанции. Binding `ROOMS` и migration `v1` не изменены.

## Протокол

Новый клиентский конверт:

```json
{"v":1,"type":"command","command":{"requestId":"уникальный-id","expectedRevision":1,"type":"attack","cardRefs":["своя-карта"]}}
```

Поддерживаются типы существующей модели `ClientCommand`:

| Команда | Поля сверх `requestId`, `expectedRevision`, `type` |
| --- | --- |
| `start_game` | нет; добавлена в общую модель |
| `attack` | `cardRefs`: от 1 до 6 уникальных идентификаторов своих карт |
| `defend` | `cardRef`, `target`: индекс атакующей пары |
| `take` | нет |
| `end` | нет |
| `pass` | нет; зарезервирован существующим ядром, в обычной партии не требуется |

`requestId` — 1–80 букв, цифр, `_` или `-`; клиент использует UUID. `expectedRevision` — неотрицательное безопасное целое число. Лишние поля запрещены, включая `playerId`, состояние, случайные результаты и параметры магии. Игрок определяется исключительно по авторизованному socket.

Ответ: `command_result` с `requestId`, `ok`, `revision`, при отказе — `code`. После принятого действия сервер рассылает персональные снимки в существующих событиях комнаты, включая `room_snapshot`:

- `game.revision`;
- `game.view`, созданный **только** через `projectGameForPlayer`;
- `game.allowed`: свои допустимые карты атаки, свои варианты защиты по целям, доступность `take` и `end`;
- `events`, прошедшие **только** через `projectEventsForPlayer`.

Чужая рука и порядок колоды никогда не отправляются. Событие чужого добора содержит только количество. Публичные карты атаки, защиты и завершённого стола доступны обоим. Проверки тестируют фактический JSON всех серверных сообщений, а не только отображение.

## Интерфейс и синхронизация

После старта лобби показывает `NetworkTable`, который работает с безопасным представлением. Собственная рука всегда снизу для обоих мест, наверху — закрытая рука соперника с его настоящим именем и статусом подключения.

Переиспользованы `OrdinaryHand`, раскладка веера и прокрутка, `TurnIndicator`, `MagicStatus`, `useTableLayout`, `BoardImpact`, `GameAnimationLayer`, очередь `useGameAnimations` и TTS. Общий компонент `TableCard` извлечён из существующего отображения карты на столе и используется также одиночным режимом. `main.tsx` не копировался. Локальный контроллер и бот продолжают работать отдельно от сетевого.

Выбор карты — локальное состояние UI; перенос карты, отбой, взятие, добор и результат появляются только после серверного подтверждения. Быстрое двойное нажатие блокируется синхронным указателем ожидающей команды. При отказе выделение сбрасывается. Если подтверждение не пришло за 12 секунд, соединение восстанавливается и запрашивается актуальное состояние; новая раздача не создаётся.

Анимации запускаются только по персональным подтверждённым событиям и дедуплицируются по ревизии. Позиции публичных карт снимаются перед обновлением React-состояния для анимации отбоя и взятия. Добор визуально начинается после ухода карт со стола, но серверный ход не ждёт CSS. При пропуске ревизий интерфейс восстанавливает стол по свежему снимку без воспроизведения пропущенной истории. Скрытые карты не подставляются в анимации.

## Как сыграть вручную

Нужен Node.js 22+. В корне frontend установите зависимости и настройте публичный endpoint, как в `MULTIPLAYER_STAGE_2.md`:

```powershell
npm ci
Copy-Item .env.example .env.local
npm run dev
```

В другом окне PowerShell, из корня проекта:

```powershell
Set-Location worker
npm ci
npm run dev
```

1. В браузере A откройте `http://localhost:5173/multiplayer`, введите имя и создайте комнату.
2. Скопируйте приглашение и откройте его в браузере B или приватном окне с отдельной сессией. Введите второе имя и присоединитесь.
3. В браузере A нажмите «Начать игру». У каждого появятся шесть собственных карт; чужие карты закрыты.
4. Игрок с атакой выбирает карту и нажимает «Атаковать». Защитник выбирает карту в своей руке, затем нажимает «Отбить» на нужной атакующей карте.
5. Атакующий может подкидывать допустимые ранги или завершить отбитую атаку. Если защитник нажал «Взять карты», атакующий ещё может подкинуть, затем завершает подкидывание. Добор выполняется сервером.
6. Продолжайте до победы или ничьей. Обновите страницу или временно отключите сеть в середине партии: после восстановления остаются тот же стол, рука и место.
7. Для новой партии после результата создайте новую комнату. Повторная раздача в текущей комнате пока не предусмотрена.

Проверки:

```powershell
npm test
npm run build
Set-Location worker
npm run check
npm test
```

## Ограничения

Магия, учебные задания, реванш в той же комнате, чат, зрители и таймер хода не реализованы. Существующая политика восстановления использует `sessionStorage`: очищенная или закрытая браузерная сессия может потерять recovery-секрет. Другой участник не получает это место по одной ссылке.

В изолированной среде Codex обычный Vite/Wrangler dev ограничен правами чтения родительских каталогов. Сервер проверен в настоящем локальном runtime через явно скомпилированные модули; это не моки WebSocket. Production-сборка проходит. Полную визуальную проверку в двух обычных браузерах следует выполнить по шагам выше; в этой среде она не подтверждена. Удалённая публикация не выполнялась.
