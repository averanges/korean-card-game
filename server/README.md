# Hangul Durak — Node.js rooms prototype

Рабочий транспортный адаптер для существующей игры. **Пока только локальная подготовка; commit, push, Render deploy и переключение GitHub Pages не выполнены.**

## Запуск из корня репозитория

Нужен Node.js 22 или 24. Все команды ниже выполняются из корня Git-репозитория:

```powershell
npm ci --prefix server --include=dev
npm run check --prefix server
npm test --prefix server
npm run build --prefix server
npm start --prefix server
```

По умолчанию сервер слушает `0.0.0.0:10000`; для другого порта установить `PORT` в окружении. Корень репозитория нужен во время сборки: сервер импортирует существующие исходники игры и `worker/src`. Сборка копирует их с преобразованием TypeScript в собственное `server/dist`, исходники не меняет. Это обычный Node.js ESM, без Cloudflare runtime.

Для локального клиента, в другом PowerShell:

```powershell
$env:VITE_ROOM_API_BASE = 'http://127.0.0.1:10000'
$env:VITE_ROOM_HEALTHCHECK = '1'
npm run dev
```

Открыть `http://127.0.0.1:5173`; два независимых браузерных профиля/приватных окна. `server/.env.example` — образец серверных переменных; Node не загружает его автоматически. `server/client.env.example` — образец **публичных переменных сборки фронтенда**, не серверных секретов.

## Переиспользование

Без изменения импортируются:

- `worker/src/model.ts`: места, SHA-256 хеши секретов и joinKey, HMAC восстановления, TTL и публичная модель комнаты.
- `worker/src/gameSession.ts`: проверка команд, ревизии, серверный RNG, запуск/ходы, учебные задания, выдача наград и персональные снимки.
- `worker/src/magicSession.ts`: длительности и доступность магии, миграция состояния, закрытые/слепые ссылки и фильтрация данных.
- `src/rooms/protocol.ts`: тот же парсер, команды, snapshots, ACK, версии и поля сообщений.
- Транзитивно `src/game-core`, `engine`, `learning`, `effects`, `trickRules`, словари и колоды. React, DOM, TTS и анимации на сервер не импортируются.

Новые `server/src/input.ts`, `room.ts`, `server.ts` адаптируют HTTP Node, очереди, WebSocket `ws`, таймеры и память. Схемы/ограничения HTTP воспроизводят Worker; правила ходов и ответы на задания не реализованы повторно. Существующий Worker/Durable Objects **не изменены**.

## Контракт и безопасность

- `POST /api/rooms`, `POST /api/rooms/:id/join`, `POST /api/rooms/:id/recover`, WS `/api/rooms/:id/ws`.
- Только два места. Имя, номер места и приглашение не авторизуют игрока. Секрет приходит в HTTPS body/первом WS-кадре; в URL секретов нет. Прикладных access/body/frame логов нет.
- Для игровых HTTP и WS обязательна точная проверка Origin без пути. Разрешены GitHub Pages, прежние Cloudflare Pages/Netlify и localhost/127.0.0.1:5173. CORS — точный Origin и `Vary: Origin`, без wildcard и cookies.
- Каждая комната сериализует join, recover, auth, команды, close и очистку. Успешная команда и receipt сохраняются без async-паузы между записями. Повторный `requestId` не выполняет ход второй раз; неправильная ревизия отклоняется.
- Единственный источник истины — сервер. Каждый сокет получает `sessionSnapshot` и `sessionEvents` только для своего места. Руки, seed, хеши, ответы на открытые вопросы, blind mappings и чужие новые карты не публикуются.
- Авторизация WS — 10 секунд; максимум 4 ещё не авторизованных сокета на комнату. 30 входящих сообщений за 10 секунд на сокет, включая ping; payload до 4096 байт, без compression. Переполнение payload закрывает соединение кодом 1009 (ограничение `ws`); это транспортное отличие от Worker, где oversized frame мог получить `invalid_message`.
- Создание комнаты: тело до 128 КиБ с колодой, без колоды до 2048 байт; join/recover до 2048 байт. HTTP headers timeout 10 с, request timeout 15 с. Дополнительно максимум 1000 API-запросов/10 с на весь процесс, 100 комнат, 1000 сокетов. Непроверенным `X-Forwarded-For` не доверяем; per-IP распределённой защиты в прототипе нет.
- При медленном клиенте буфер отправки >1 МиБ закрывается. До 10000 receipts на комнату: они не вытесняются ради возможности безопасного повтора. После лимита новые команды получают `room_capacity`; такой предел не ожидается в обычной партии. Заполненный процесс возвращает 503 `server_busy`.
- Новое авторизованное соединение закрывает прежнее кодом 4009. Старый `close` не сбрасывает присутствие нового сокета. Клиент перестаёт бесконечно перехватывать место в заменённой вкладке.
- Ожидающая комната — 4 ч, активная — 24 ч от действия/подключения; heartbeat сам по себе не продлевает TTL. Истечение закрывает сокеты кодом 4004, удаляет игровое и секретное содержимое; короткая запись об истечении остаётся до часа.

Диагностика сохранена: `/health`, `/diagnostics.html`, `/diagnostics.js` и тестовый `/ws`. Только публичный `/health` имеет `Access-Control-Allow-Origin: *`, чтобы продолжала работать локальная диагностическая HTML-копия с Origin `null`. Он не содержит данных комнат и секретов. `service: hangul-durak-render-probe` сохранён для существующей диагностической страницы; добавлено `mode: rooms-memory`. Открытый `/ws` обслуживает только прежние тестовые ping/pong, **не игровые комнаты**. Игровые endpoints по-прежнему требуют точный разрешённый Origin.

## Что именно восстанавливается

Во время жизни одного процесса: refresh, закрытие вкладки, временный обрыв, повторный вход и персональный код восстанавливают прежние места, руки, стол, эффекты, счётчики наград, открытые задания и receipt. Клиент продолжает хранить секрет в существующем браузерном хранилище; формат персонального кода не меняется.

**После перезапуска, redeploy или засыпания Render все комнаты этого прототипа теряются.** `Map` и receipt существуют только в памяти; нет БД, файлового сохранения, репликации, переноса живых комнат из Cloudflare и защиты от серверного сбоя. Секрет не может восстановить уже потерянную комнату. Клиент показывает понятное сообщение вместо обещания, что партия сохранена. Для следующего этапа нужно транзакционное постоянное хранилище состояния, секретной модели и receipts.

Free Render может засыпать после 15 минут без входящего трафика и запускаться около минуты. Перезапуски возможны независимо от активности. Активные клиентские ping могут предотвращать простой, но не являются гарантией хранения/доступности. [Официальные ограничения](https://render.com/docs/free).

## Холодный старт и клиент

Для `.onrender.com` автоматически, а для custom/local host при `VITE_ROOM_HEALTHCHECK=1`:

1. Безопасный GET `/health`, ожидание до 90 секунд; 5xx/HTML холодного старта или временная сетевая ошибка могут вызвать повтор только GET. Видны этап и прошедшие секунды, без процентов.
2. Создание/join/recover выполняются прежним POST с 12-секундным лимитом, **без автоматического повторного создания комнаты**.
3. При восстановлении сохранённого места Render сначала проверяется `/recover`; missing/expired комната не превращается в новую раздачу. Затем WS/auth до 12 секунд, отдельный этап и ошибки. Heartbeat, backoff и безопасная замена вкладки сохранены.
4. Неуспешный HTTP позволяет повторить форму/подключение; WS reconnect ограничен прежними 8 попытками. Отмена компонента/pagehide прекращает ожидание health. При возвращении проверка возобновляется.

Для Cloudflare без указанного флага добавленная health-проверка **не включается**. Одиночная игра не использует эти этапы.

## Публикация — только по отдельному разрешению

Порядок: сначала Node backend, затем frontend. Сейчас это инструкция, а не выполненная операция.

1. Создать отдельный проверенный коммит в `multiplayer`, учитывая посторонние файлы рабочего дерева. Согласовать push/автоматические frontend deploy: обычный push в эту ветку может запускать существующие публикации. Если сначала публикуется только backend, использовать поддерживаемые площадками commit skip-флаги и ручной deploy Render. До готовности backend не переключать API.
2. В **существующем тестовом** Render-сервисе с URL `https://korean-card-game.onrender.com` открыть Settings. Не создавать новый Blueprint вслепую: имя dashboard-сервиса может отличаться от `name` шаблона `render.yaml`.
3. Root Directory очистить (корень Git-репозитория). Build Command:

   ```text
   npm ci --prefix server --include=dev && npm run check --prefix server && npm run build --prefix server
   ```

   Start Command: `npm start --prefix server`. Plan Free, Node 22, `/health`, auto deploy Off. Для ручной настройки Root Directory — пустая строка, в YAML используется `.`. Регион существующего сервиса сохранить.
4. Установить `FRONTEND_URL=https://averanges.github.io/korean-card-game` и `ALLOWED_ORIGINS` из `server/.env.example`. Если у сервиса уже есть дополнительные реальные Origin, сохранить их. `PORT` назначает Render. Не копировать Worker/Cloudflare API tokens. `FRONTEND_ORIGIN` Worker не трогать.
5. Выполнить ручной deploy только после разрешения. Проверить `/health`: `ok:true`, `mode:rooms-memory`; `/diagnostics.html`, тестовый WS, CORS OPTIONS с `https://averanges.github.io`, создание и две реальные сессии на тестовом клиенте.
6. В GitHub → repository Settings → Secrets and variables → Actions → **Variables** задать публичные repository variables:

   ```text
   VITE_ROOM_API_BASE=https://korean-card-game.onrender.com
   VITE_ROOM_HEALTHCHECK=1
   ```

   В подготовленном workflow переменная API имеет прежний Cloudflare fallback; сейчас реальная repository variable не менялась. Для переключения нужен rebuild/deploy GitHub Pages. Workflow по-прежнему использует Node 22 и base `/korean-card-game/`.
7. Запустить Deploy GitHub Pages вручную из `multiplayer` после разрешения. Приглашения строятся на фронтенде через `withBase`, а REST также возвращает GitHub Pages URL. В ссылке комнаты backend URL не хранится; оба клиента используют один API, зафиксированный сборкой. Старые вкладки могут содержать прежнюю сборку — обоим игрокам обновить страницу и создать **новую** комнату.
8. Проверить из России и Кореи начало/ходы/магические задания/refresh. Для отката вернуть repository variable на прежний Worker, выключить health-флаг и пересобрать Pages. Живые комнаты автоматически между серверами не мигрируют.

Подробные результаты проверок: `docs/render-multiplayer/REPORT.md`.

## Повтор браузерных проверок

`scripts/check-render-browser.mjs` и `scripts/check-render-wake.mjs` проверяют настоящий frontend и Node backend. Нужны установленный Playwright и браузер (либо доступный модуль через `PLAYWRIGHT_MODULE`, исполняемый браузер через `CHECK_BROWSER`). Браузерные зависимости не входят в runtime сервера.

Подготовить production Pages-сборку с локальным API и health-флагом, обслуживать её под `/korean-card-game/` с настоящим 404 fallback, разрешить Origin этого локального preview в Node. Задать `CHECK_APP_URL` равным базовому адресу preview, например `http://127.0.0.1:4178/korean-card-game`. Затем из корня репозитория:

```powershell
node scripts/check-render-browser.mjs
node scripts/check-render-wake.mjs
```

Первый скрипт создаёт настоящую тестовую комнату и двух участников, делает ход, защиту, refresh и автоматическое восстановление после обрыва WS. Если случайная раздача не допускает ни одной защиты первой атаки, он пробует новую настоящую комнату (не более шести), не подменяя карты. Второй моделирует только задержку/ошибки health для проверки UI; POST успешного сценария идёт в настоящий backend. Не запускать эти скрипты против чужих или рабочих комнат: они создают собственные новые тестовые партии, по умолчанию обращаются только к локальному preview.
